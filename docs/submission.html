01项目背景

OpenFix 关注的是设备报警发生之后的“半小时”。这半小时里，现场人员必须完成三件事：判断报警指向什么、确认哪些处置是安全的、留下可复核的记录。而支撑这三件事的知识，通常并不在同一个地方。

三个真实缺口

知识载体现状后果
设备手册与 SOPPDF 动辄数百页，报警码分散在不同章节定位慢，现场往往直接跳过，凭经验处置
老师傅经验存在于个人记忆中，未结构化沉淀人员流动即知识流失，同类故障反复排查
历史工单Excel 或纸质记录，字段不统一、无法检索相似案例无法复用，重复停机与不必要的备件更换
通用 AI 助手可以流畅生成维修步骤，但无法给出可核验的来源在高温、带压、带电场景中，编造的步骤本身即风险

中小制造企业普遍缺少专职知识工程团队，也没有预算部署复杂的 RAG 基础设施。因此问题不在于“有没有 AI”，而在于能否用可部署、可验证的方式，把分散的维修知识变成可追溯的判断依据。

目标用户

  • 中小制造企业的设备部与维修班组——报警后的第一响应人。
  • 动力站、加工线、包装线等高关键设备的值班维护人员。
  • 为制造企业提供设备运维服务的系统集成商——需要可私有化交付的工具。
  • 建设行业设备知识库的开源社区与科研机构。
项目不做什么

OpenFix 不替代维修人员判断，不输出“可直接执行”的指令，不承诺诊断准确率。它只做一件事：把证据整理到位，把风险拦住，把决定权和责任留在授权人手里。

02解决方案与应用场景

OpenFix 是一个本地优先的检修决策工作台。现场人员用一句自然语言描述现象，系统返回一个可核验的证据包，而不是一段无法追溯的建议。

工作流

  1. 现场人员输入设备编号、报警代码和异常现象（中英混合、口语化均可）。
  2. 系统识别设备与报警码，联合检索 SOP、安全规程与历史工单。
  3. 结构化约束确保报警码精确匹配，相近报警码的工单不进入同一证据包。
  4. 确定性安全规则独立评估风险，命中即前置安全处置并阻断危险动作。
  5. 输出故障假设、逐条证据来源、信息缺口与建议检查步骤。
  6. 普通诊断可转为待审批工单，批准或驳回均写入 SQLite 审计轨迹。

三个典型场景

SCENE 01 · 诊断取证
空压机排气温度高
AC-01 空压机报 E201，排气温度高，复位后很快又停机
系统行为
识别设备 AC-01，锁定报警码 E201，命中对应 SOP 与“冷却器堵塞”历史工单，输出证据链与缺失信息。
设计要点
同设备的 E203 工单不会作为等价证据混入；证据不足时明确列出需要补充的量测数据。
SCENE 02 · 安全拦截
带压拆管请求
空压机压力还在，要求直接拆油管检查
系统行为
安全状态升级为“需要安全复核”，强制前置引用通用能量隔离规程，只输出停机、泄压、零能量验证步骤，并将“带压拆管”列为禁止动作。
设计要点
该结论由确定性规则产生，不依赖检索分数，也不参与语言生成——即使用户明确要求，系统也不会顺从。
SCENE 03 · 主动拒答
问题超出维护领域
今天产量怎么样
系统行为
放弃推断，返回需要补充设备、报警与现场状态的提示。
设计要点
在工业场景里，“不确定却给出步骤”比“明确拒答”危险得多。拒答是功能，不是失败。

与通用 AI 助手的边界

维度通用 AI 助手OpenFix

三个关键工程决策

1. 用结构化约束弥补检索的不可靠

纯 BM25 在小语料上表现尚可，但会把“同一台设备的其他报警码”当成强相关证据。OpenFix 在排序前先做一次硬约束：只要查询中出现已知报警码，就只保留同码的 SOP 与同码历史案例，再做相关性排序。这条约束带来的是可解释的确定性——解释“为什么这条证据进来了”比解释“为什么它的分数是 0.47”容易得多。

2. 把安全政策从检索里剥离出来

安全判定不读取检索分数，也不交给语言模型。它是独立的一组规则函数，输入只有现场描述，输出是风险类别、禁止动作与安全处置。这样做的直接好处是：安全门槛可以被单元测试穷举验证，不会因为知识库内容变化而漂移。

3. 状态机 + 条件更新

工单审批采用 UPDATE ... WHERE status = 'pending_approval' 并检查受影响行数，从数据库层杜绝两位审批人同时通过同一张工单。

04创新点

本项目不追求“更强的模型”，而是把工业维护场景里真正稀缺的东西工程化：可追溯、可拦截、可测试。

1. 证据与执行分离

系统只生成“诊断证据包”，不生成执行许可。执行需要授权人批准，高危条件下只输出安全处置与补充信息要求。这一条把 AI 的输出 与 人的决定 在架构上隔开，而不是靠提示词约束。

与已有方案的差异：多数“AI 维修助手”把建议直接当作答案交付，责任边界模糊；本项目在数据模型里就把「证据」与「工单执行」拆成两个状态。

2. 报警码优先的结构化检索

中文 BM25 解决术语与口语化表达的匹配，报警码与资产类型约束解决准确性。E201 的诊断不会把同设备的 E203 工单当作等价证据，也不会把 E2010 误判为 E201。

可验证证据：评测集专门设置“同设备不同报警码干扰”用例，证据召回率 100%；单元测试覆盖报警码边界与设备别名歧义。

3. 可测试的确定性安全政策

6 类风险规则以代码实现，输入现场描述，输出风险类别与禁止动作。规则不读检索分数，不依赖模型，因此可以被穷举测试，也可以在评审时逐条复核。

可验证证据：安全门命中率 100%；“拆开正在运行的风机护罩”这类非固定短语表达，通过“动作 + 部件 + 运行状态”的复合条件命中旋转设备规则。

4. 主动拒答

输入为空、与维护无关、或证据不足以支撑结论时，系统明确拒绝推断，并说明缺什么。工业场景下，一个“不知道”比一个错误答案有价值。

可验证证据：拒答准确率 100%，覆盖空输入、纯空白、跨领域提问三类用例。

5. 本地优先、零第三方依赖

后端只使用 Python 标准库，检索与分词自行实现，持久化用 SQLite，无云 API、无向量数据库、无外部服务。这意味着：可以在断网的工控机上运行，可以被完整审计，也不会因为某个上游服务的价格或策略变化而失效。

与已有方案的差异：主流 RAG 方案要求向量库与嵌入模型，部署门槛与数据合规成本都不适合中小制造企业；本项目用“结构化约束 + 轻量检索”换取了可部署性。

“零第三方依赖”不只是部署便利，也是安全策略：没有 npm / PyPI 依赖树，就没有传递依赖漏洞与许可证污染。唯一的二进制是 Python 运行时本身，来源与许可证可核验。

07长期发展

路线图

阶段方向内容
近期CMMS / EAM 对接接入企业工单与设备主数据，让审批结果回到既有系统，形成知识回流

中期传感器数据测量趋势分析与事件时间窗，把“排气温度高”变成可量化的判断依据

试点计划（4 周）

  1. 脱敏导入 100—300 份设备手册与历史工单。
  2. 由维修主管审核 100 条真实故障描述，作为评测基线。
  3. 对比接入前后的首轮定位时间、重复停机率与工单返工率。
  4. 记录安全规则的误报、漏报与人工纠正原因。
  5. 将已验证工单回灌知识库，保留版本与审核人信息。

试点的价值不在于再跑一次 100%，而在于拿到第一组真实数据：首轮定位时间是否缩短、返工率是否下降、安全规则在真实描述下的误报率是多少。这些数字决定项目下一步往哪走。

08风险与边界

风险现状应对
数据为合成数据未使用真实工厂数据，未做生产验证以 4 周试点获取真实基线，公开测量口径
无真实身份认证演示版审批人仅为姓名字段生产部署必须接入企业 SSO 与服务端细粒度授权
安全规则覆盖有限6 类关键词与复合条件规则，覆盖演示场景结合企业危险源清单、作业许可制度与专家评审扩充
小规模检索BM25 适合当前离线语料规模大规模知识库需切分、权限过滤与向量混合检索
大模型接入风险当前版本未接入生成式模型接入后需评估提示注入、越权检索与输出越界
人工审批≠安全认证系统记录“谁批准了什么”不能替代现场 LOTO、工作票与设备隔离程序
设计原则

没有证据不诊断，没有审批不执行。这条原则写在代码里，而不只是写在文档里：证据不足时引擎返回拒答，未审批的工单不能进入执行状态，高危场景下安全处置优先于用户请求。
