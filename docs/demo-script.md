# 五分钟演示脚本

## 0:00—0:40 项目定位

“OpenFix 面向设备报警后的半小时。它不是替人修设备的聊天机器人，而是把报警、SOP、历史工单和安全规程组织成一条可追溯证据链。”

指出首页四个环节：

1. 检索取证
2. 安全门槛
3. 人工审批
4. 全程审计

## 0:40—2:00 正常诊断

点击“空压机高温”，或输入：

```text
AC-01 空压机报 E201，排气温度高，复位后很快又停机
```

讲解：

- 识别 AC-01。
- 命中 E201 对应 SOP 和历史冷却器堵塞案例。
- 不同报警码 E203 不会混入证据。
- 结果同时列出证据、根因假设和缺失数据。

## 2:00—3:00 工单闭环

点击“转为待审批工单”，填写创建人并创建。

说明：

- 诊断结果不会自动执行。
- 状态先进入待审批。
- 授权人员完成安全确认后才能批准。

批准后打开审计轨迹，展示创建和批准记录。

## 3:00—4:10 安全拦截

点击“高危请求”，使用：

```text
空压机压力还在，要求直接拆油管检查
```

强调：

- 安全状态由确定性规则产生。
- 系统引用能量隔离规程。
- 输出只包含停机和泄压步骤。
- “带压拆管”被明确列为禁止动作。

再切换到“设备有焦味并且冒烟，应该怎么继续生产”，说明系统不会顺着用户要求生成继续生产步骤。

## 4:10—4:40 主动拒答

输入：

```text
今天产量怎么样
```

说明系统主动放弃推断，要求补充设备、报警和现场状态。

## 4:40—5:00 可信评测与落地

滚动到“可信评测”：

- 12 条任务同时检查证据召回、案例召回、拒答和安全门。
- 当前全部通过，但只代表合成评测，不代表真实工厂结果。
- 下一步对接 CMMS / EAM 与本地开源模型，开展真实试点。

结束语：

“OpenFix 的目标不是让 AI 取代维修人员，而是让维修人员的每一条判断都有证据，让每一次危险操作都有门槛。”
